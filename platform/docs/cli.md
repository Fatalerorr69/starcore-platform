# CLI Reference

The `starcore` CLI (`apps/cli/main.py`, Typer) is a thin delivery layer over
the same domain packages the HTTP API uses — see [Architecture](architecture.md).
Every command below is generated by reading the actual command signatures,
not transcribed from memory; if a flag looks wrong, the source has moved.

## Top-level commands

| Command | Description |
|---|---|
| `starcore version` | Print the installed STARCORE version. |
| `starcore health` | Local liveness check mirroring `GET /health` (database connectivity only). Exit 0 = healthy, 1 = unhealthy. |
| `starcore doctor [--fast] [--json] [--quiet]` | Run all local quality gates: lockfile check, ruff lint/format, pyright, pip-audit, bandit, and (unless `--fast`) the test suite. Exit 0 = all gates passed, 1 = one or more failed. |
| `starcore audit [--json] [--quiet]` | Quick local project-state summary: git branch/SHA/working-tree status, file counts, runtime environment, OS platform. Exit code is always 0. |
| `starcore diagnose [--json] [--quiet]` | Deep health/status check of the deployment and configured providers — the CLI equivalent of `GET /diagnostics`. Exit 0 = overall status `ok`, 1 = `warning` or `error`. |
| `starcore plugins` | List plugins discovered under `plugins/` and whether each loaded successfully. |

`--json` (where offered) emits a machine-readable object instead of a Rich
table — see each command's docstring in `apps/cli/main.py` for its exact
JSON schema. `--quiet` suppresses all output and relies on the exit code
alone; useful for cron/systemd health checks.

## `starcore blueprint`

| Command | Description |
|---|---|
| `starcore blueprint plan <path>` | Show the dependency-ordered execution plan for a blueprint YAML file, without running it. |
| `starcore blueprint run <path> [--parallel]` | Execute a blueprint. Default: sequential (`BlueprintExecutor`). `--parallel`: concurrent, wave-based (`Scheduler`) — see [ADR-001](adr/ADR-001-blueprint-dependency-execution.md) for why both produce identical dependency orderings, and [ADR-010](adr/ADR-010-dependency-failure-semantics.md) for what happens when a dependency fails. |

## `starcore runs`

| Command | Description |
|---|---|
| `starcore runs list` | List persisted blueprint run history. |
| `starcore runs show <run_id>` | Show the per-task results of one persisted run. |

## `starcore ai`

| Command | Description |
|---|---|
| `starcore ai generate "<description>" [--output/-o <path>]` | Translate a natural-language description into a validated blueprint YAML via the configured `AIProvider` ([ADR-007](adr/ADR-007-ai-provider-abstraction.md)). Prints the generated YAML and a plan-style table (including `depends_on`); with `--output`, writes the YAML to a file instead of stdout. Requires `STARCORE_ANTHROPIC_API_KEY` (default provider) or `STARCORE_AI_BASE_URL` + `STARCORE_AI_MODEL` (openai-compatible provider) — see [Installation](installation.md#configuration-reference). |

## `starcore proxmox`

| Command | Description |
|---|---|
| `starcore proxmox discover` | Audit the configured Proxmox host: node CPU/RAM/disk, storage pools, available VM/LXC templates, network bridges, and existing resources. Requires `STARCORE_PROXMOX_*` credentials. |

## `starcore resource`

| Command | Description |
|---|---|
| `starcore resource action <provider> <action> <resource> [--node] [--vmid] [--kind]` | Run a single lifecycle action (`start`/`stop`/`shutdown`/`destroy` for Proxmox, `start`/`stop`/`remove` for Docker) against one resource, independent of any blueprint. Exit 1 if the action fails. |

## `starcore snapshot`

Proxmox VM/LXC snapshot management. `delete` and `rollback` are destructive
and prompt for confirmation unless `--yes`/`-y` is passed — this is the
CLI's actual automation mechanism for destructive operations (not
`--non-interactive`, which was removed from the read-only reporting
commands above because it never controlled anything on them).

| Command | Description |
|---|---|
| `starcore snapshot create <node> <vmid> <name> [--kind vm\|lxc] [--description]` | Create a snapshot. |
| `starcore snapshot list <node> <vmid> [--kind vm\|lxc]` | List snapshots. |
| `starcore snapshot delete <node> <vmid> <name> [--kind vm\|lxc] [--yes/-y]` | Delete a snapshot. Prompts unless `--yes`. |
| `starcore snapshot rollback <node> <vmid> <name> [--kind vm\|lxc] [--yes/-y]` | Roll back to a snapshot, discarding current state. Unless `--yes` is passed, first shows the resource's current status and a config diff (only fields the Proxmox API actually returns for both the current config and the snapshot's config — never a fabricated diff; says so explicitly if the API can't provide one), then prompts for confirmation. |

## Exit codes

Across all commands: `0` means success (or, for `audit`, that it ran at
all — it never fails), non-zero means at least one check/gate/task failed.
`doctor`, `diagnose`, `blueprint run`, and `resource action` are the
commands automation should actually check the exit code of; `audit` is
informational only.
